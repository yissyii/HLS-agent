# 第 1 篇：面向 HLS 的 C/C++ 自动修复

## 阅读信息

- 论文：*Automated C/C++ Program Repair for High-Level Synthesis via Large Language Models*
- 作者：Kangwei Xu、Grace Li Zhang、Xunzhao Yin、Cheng Zhuo、Ulf Schlichtmann、Bing Li。
- 参考文献编号：`[28]`；本次参赛价值排序：第 1 名。
- 本地论文：[28-Automated-C-Cpp-Program-Repair-for-HLS.pdf](28-Automated-C-Cpp-Program-Repair-for-HLS.pdf)
- 在线来源：[arXiv:2407.03889](https://arxiv.org/abs/2407.03889)
- 讨论日期：2026-09-15。
- 状态：本篇要点讲解及用户提问已结束，完成归档。
- 范围：依据本地 9 页 PDF 和对话整理。论文实验未在当前参赛系统中复现；下文区分原文结果、用户回答和比赛应用建议。

## 一、最重要的结论

这篇论文最值得迁移的是：把工具报错、经过验证的修复知识和模型修改串成可重复验证的流程。

针对当前 HLS 比赛，讨论形成的建议是：

1. 用 Vitis 官方文档和示例启动本地知识库，再持续加入真实失败案例。
2. 优先提高错误反馈修复能力，并用同一个模型的固定裸基线衡量增益。
3. 必须保证位宽、符号和接口语义正确；进一步缩减已正确代码的位宽，暂不作为每题必经步骤。
4. 智能体内部的分析脚本和最终提交的 HLS 源码应有明确的输出边界。
5. 是否启用额外检索、分析或优化，由开发集上的通过率和墙钟时间实测决定。

## 二、论文解决的问题

普通 C/C++ 面向处理器执行，HLS 需要把程序映射为具有确定结构和资源的硬件。能在普通编译器上运行的程序，未必能直接综合。

论文关注指针相关限制、动态存储、递归、位宽和其他不兼容写法。传统转换脚本只能覆盖部分模式，直接让 LLM 修复也可能产生新错误，并消耗多轮调用。

作者希望输入已有 C/C++ 程序，自动生成兼容 HLS 的版本，并进一步优化硬件实现。

注意：这是“已有程序的转换与修复”任务。比赛中从题目生成代码后再修复，属于对其方法的迁移，不能直接沿用论文成功率。

## 三、方法要点

### 3.1 整体流程

原文图 2 位于 PDF 第 3 页，描述五个阶段：

1. **预处理**：调用 HLS 工具获取实际错误，再让模型结合常见不兼容类型分析潜在问题。
2. **检索增强修复**：检索相关修复模板，提供给模型；修改后重新编译，失败则根据反馈继续修复。
3. **位宽优化**：让模型生成分析程序，结合场景、数据描述和运行中获得的变量范围调整类型。
4. **验证**：进行 C/RTL 协同仿真，以原程序及测试基准检查结果。
5. **PPA 优化**：识别性能瓶颈，检索优化策略，调整代码和工具指令。

其中 PPA 指性能、功耗和面积。论文还采用“脚本先处理简单问题、模型再处理剩余问题”的协同方式降低调用成本。

### 3.2 RAG 修复库

RAG 是检索增强生成：先从外部资料中找相关依据，再把这些依据放入模型上下文。

本论文的修复库依据人工经验和 HLS 手册建立。条目包含错误信息、不兼容示例、修复指导和正确示例，再通过相似度检索选择相关内容。

例如，检测到递归问题后，向模型提供改成迭代的规则和示例。模板可以减少模型凭记忆猜测，但其适用条件和正确性仍需要验证。

### 3.3 位宽优化

原文示例中，变量 `m` 的观测范围为 `0～481`。9 位无符号整数可以表示 `0～511`，因此作者将该变量从普通整数改成 Catapult 的任意精度类型。

需要区分两种依据：

- **观测范围**：这批测试数据中出现过哪些值。
- **可保证的范围**：所有合法输入和中间计算都不可能超出哪些界限。

前者不能单独证明后者。原文称其方法为静态位宽优化，但示例及附录也包含执行程序、统计变量范围的过程，不能仅凭“静态”一词就认为它提供了全输入范围证明。

### 3.4 树结构改写示例

PDF 第 7 页图 9 展示了三种转换：

| 原始实现 | 改写方向 | 必须核对的条件 |
|---|---|---|
| 指针连接树节点 | 用数组下标连接节点 | 空节点标记、下标有效范围、节点关系 |
| 动态分配节点 | 预分配静态节点池 | 最大节点数及容量边界 |
| 递归调用 | 用有界的显式栈进行迭代 | 栈容量、状态恢复、访问顺序 |

**对前面讲解的修正**：论文将这个例子标为 BFS，但展示的递归访问和显式栈形态更接近深度优先遍历，且代码有省略。应把它作为树结构转换示例阅读，不能将片段当作完整、已核验的标准 BFS 实现。

## 四、实验设置与结果

### 4.1 设置

- 24 个应用，覆盖论文划分的 8 类不兼容问题。
- GPT-4 Turbo，经 API 调用。
- Catapult HLS；运行环境为 Intel Xeon Silver 4314 CPU。
- 使用 Synopsys Design Compiler 和 Nangate 45nm 标准单元库进行逻辑综合。
- 每个应用重复 15 次实验，每次实例允许进行多轮修复，文中设置为 5 次调用。
- 表 II 分别报告编译和仿真通过率；成功实例数除以总实例数得到通过率。

因此，表中通过率不能当作裸模型一次生成的 pass@1，也不能直接等同比赛中的 pass@5。

### 4.2 作者报告的结果

| 结果 | 比较对象及口径 | 位置 |
|---|---|---|
| 平均仿真修复通过率提高 23.33 个百分点 | 完整框架相对直接使用 GPT-4 Turbo；按通过率差理解，原文写作 23.33% increase | PDF p6，图 6 及正文 |
| 平均仿真修复通过率提高 13.89 个百分点 | 完整框架相对 GPT 与脚本结合、未使用 RAG 的消融方案 | PDF p6，图 6 及正文 |
| 面积、功耗、最小时钟周期平均降低 36.57%、33.03%、29.08% | 位宽优化实验相对默认 32 位整数实现；不能理解为全部 24 个应用都取得同样收益 | PDF p6，图 7(a) |
| LLM 成本平均降低 21.56% | 在成功修复程序中，按输入输出 token 及当时 API 价格统计脚本预修复的收益 | PDF p6，图 7(b) |
| 面积、功耗、最小时钟周期平均降低 14.02%、11.50%、17.94% | 对 6 个存在性能瓶颈的案例进一步优化 | PDF p6，图 8 |

上述结果均为作者报告。API 费用减少不等于本地模型墙钟时间按相同比例减少；ASIC 标准单元库结果也不等于比赛 FPGA 上的资源和时序结果。

## 五、用户对思考题的回答与讨论

### 5.1 为什么加入 RAG 模板库？

用户回答：

> RAG模板库可以降低LLM的工作需求，优化工作效率，且解决方案更加稳定

讨论结论：方向正确。模板给模型提供经过验证的依据，有助于减少猜测和重复试错。但检索和额外上下文也有成本；是否更快、更稳定，要看它是否减少失败和后续重试。

### 5.2 先做位宽优化，还是错误反馈修复？

用户回答：

> 优先错误反馈修复，因为错误反馈修复更能提升基线

讨论结论：优先顺序正确。表述应改为“提高智能体相对固定裸基线的增益”。裸基线需要保持规定配置，才能衡量新增修复机制的贡献。

### 5.3 为什么最大观测值为 481，也不能直接断定 9 位足够？

用户回答：

> 最小值不确定是否为负数

讨论结论：负数会影响符号类型和所需位宽，是一个有效风险点。但论文示例已经观测到最小值为 0；更根本的问题是观测范围不一定覆盖所有合法输入。

即使已测输入只产生 `0～481`，另一组合法输入也可能产生 700，而 9 位无符号整数最多表示 511。应根据题目约束和计算过程推导范围，再考虑缩减位宽。

## 六、用户问题一：RAG 库能否借用现有资料？

### 问题

> RAG库的建立应该是一个长期的过程，我除了在准备比赛的过程中人为编写这个库，是否能借用其它现有的库？

### 回答与结论

可以。建议用可靠的官方资料启动，再加入当前模型和工具版本下的失败经验。这些资料是修复库的内容来源，需要筛选和整理；它们不自动等于已经适配比赛的修复模板库。

> 版本边界：当前运行和验证工具链已切换到 Vitis HLS 2026.1。本节的 UG1399 2025.2 引用及规则记录保留为历史参考，不能单独证明 2026.1 兼容性；涉及工具行为的结论必须在 2026.1 环境重新验证。现有 RAG 语料仍明确绑定 UG1399 2025.2。

| 来源 | 内容 | 当前用途 |
|---|---|---|
| [Vitis HLS 2025.2 官方手册 UG1399](https://docs.amd.com/r/2025.2-English/ug1399-vitis-hls) | 语言限制、类型、接口、循环和优化规则 | 规则依据，优先使用 |
| [Vitis HLS Introductory Examples](https://github.com/Xilinx/Vitis-HLS-Introductory-Examples) | 数组、接口、任意精度类型、流水线等示例，附测试台及运行配置 | 提炼小型正确示例，并在参赛环境验证 |
| [Vitis Libraries](https://github.com/Xilinx/Vitis_Libraries) | 数学、线性代数、DSP、图像等算法实现 | 遇到对应任务时参考局部实现，检查依赖和平台要求 |
| 自己的开发失败记录 | 原候选、工具诊断、修改过程及验证结果 | 逐渐形成最贴合当前比赛的修复库 |

建议先以十几条高频规则验证收益。这个数量只是起步建议，不是论文的实验结论。初期用错误类别或关键词检索即可，有需要后再引入向量检索。

模型可以辅助提炼资料，但入库前应核查规则并运行测试。推荐每条规则保存：

```text
问题：使用动态内存分配
适用条件：题目明确给出最大数据规模
修复思路：改为有确定容量的静态存储
必须保留：有效长度、索引语义和边界行为
不适用：无法确定容量上界的情况
验证方式：编译、功能测试、综合
来源：官方章节和对应示例
版本：Vitis 2025.2
```

只有“把 malloc 改成数组”一句话不够：如果模型随意选择数组容量，就可能在隐藏测试上失败。

### 版本和维护边界

- 固定与 Vitis 2025.2 相容的资料版本或提交，保留来源及许可证信息。官方仓库默认分支会变化。
- Vitis Libraries 的 README 说明，部分库自 2025.2 起停止维护，因此不能默认旧示例和当前环境完全一致。
- 准备期间可以持续积累；本地比赛指南要求正式评测窗口内不得修改方案代码、技能包和模型权重，需要提前冻结正式参赛资料。
- 开发评测题及答案应与知识库内容保持清楚的隔离，避免用近重复答案得出不可信的泛化结论。
- 本次讨论没有确认本论文完整修复库可直接下载复用，因此未把它列为已获得资源。

## 七、用户问题二：位宽处理是否必要，如何避免输出混淆，收益是否值得？

### 问题

> 位宽的处理在我们的比赛中是必须的吗？LLM生成的位宽处理脚本会不会被比赛的测试平台错误提取为HLS代码？位宽处理占用的模型性能和产出代码质量的提升在比赛中是否是有益的？

### 7.1 必要性：区分正确性与进一步压缩

| 工作 | 当前优先级 | 原因 |
|---|---|---|
| 遵守题目接口的类型、符号和位宽 | 必须 | 影响接口匹配和功能语义 |
| 修复中间运算的溢出、错误截断或符号扩展 | 必要时必须 | 直接影响测试结果 |
| 缩减已经正确的较宽内部类型 | 可选，暂不默认启用 | 主要改善资源或时序，需要衡量额外成本 |

例如，两个值域均为 `0～255` 的数相加，完整结果范围为 `0～510`，需要至少 9 位无符号表示。但如果题目要求 8 位回绕结果，则应保留该截断语义，不能自行改变行为。

本地指南的权重为：加权通过率 30、相对同模型裸跑增益 40、墙钟效率 10、智能体与技能包工程质量 20。没有单独列出面积、功耗或位宽优化得分。

结论：论文的 PPA 提升不能直接换算成比赛加分。功能正确后，仅在优化有助于实际判定或确有实测收益时启用；最终公式、阈值和预算仍以赛事后续细则为准。

### 7.2 输出混淆：当前代码确实需要区分内部工具与最终源码

讨论时检查了项目的 [extract_code](single_task.py) 函数。以 2026-09-15 看到的实现为准：

- 纯文本响应会整体作为源代码。
- 单个完整 C/C++ 代码块会去掉外层标记后作为源代码。
- 多代码块或夹带说明会报格式错误。

提取器没有能力判断任意一段 C++ 是“分析工具”还是“待综合函数”。如果模型只返回了位宽分析程序，该程序可能通过文本提取，随后在编译或验证中失败。

未来若实现位宽优化，应设计为：

```text
智能体内部：分析范围 → 修改候选 → 验证结果
最终输出：只包含符合题目接口的完整 HLS 源码
```

分析脚本、报告和日志应保存到内部工作文件，不混入最终代码响应或最终源码文件。当前指南未给出正式评分器的具体提取实现，不能假定它会自动区分这些用途。

本次仅做了代码阅读，没有修改或运行新的位宽优化模块。

### 7.3 成本与收益：暂不每题动态生成分析脚本

生成分析程序、执行分析、修改候选和再次验证，都会消耗总预算；范围估计错误还可能降低正确率。

当前建议：

1. 在首次生成时遵守接口、符号和基本运算范围规则。
2. 出现溢出、截断等实际功能错误时，触发针对性修复。
3. 功能已正确、报告显示相关资源或时序瓶颈时，再考虑缩减位宽。
4. 根据明确上下界计算所需位数等固定工作，由普通程序完成，不必每题让模型重新编写工具。
5. 在相同模型、题集和总预算下，对比启用前后的最终通过率、回归错误和墙钟时间，再决定是否保留。

“硬件资源占用降低”和“模型推理开销降低”是不同收益，需要分别记录。

## 八、阅读中需要保留的修正与限制

1. **指针不是一律不支持。**前面讲解将“指针”概括为错误过于宽泛。Vitis 支持部分可以静态分析的指针用法，应按具体形式和工具规则判断。
2. **修复保持语义。**加边界检查、改存储结构或改遍历方式，都可能改变行为；不能只根据编译通过认定修复正确。
3. **有限测试不构成完整等价证明。**原文将 C/RTL 协同仿真称为等价验证，应理解为相应测试覆盖下的结果一致，不能直接推断所有输入都等价。
4. **Catapult 与 Vitis 需要适配。**论文中的 `ac_int`、`hls_unroll` 等类型或指令不能原样当成 Vitis 2025.2 规则。应转换到目标工具支持的接口并重新验证。
5. **原文树遍历片段需谨慎。**BFS 标签与展示形态之间存在疑点，见 3.4 节；不能复制省略片段作为已验证实现。
6. **本文建议尚未验证收益。**排序靠前说明它值得优先尝试，不保证一定提高当前模型的比赛成绩。

## 九、后续实验建议（尚未实施）

首个实验建议只验证“错误反馈中加入适用的修复规则”是否有效：

| 对照 | 内容 |
|---|---|
| 裸基线 | 按比赛要求，仅题目、单次生成、不重试、不调用工具 |
| 修复对照组 | 同模型，加入普通工具反馈和有界修复 |
| 规则增强组 | 在修复对照组上加入少量已验证模板 |

各修复组保持相同总时间和修复次数上限。记录四阶段结果、成功修复题数、引入的回归、重复错误、模型调用与总耗时。

由此分别判断“反馈修复是否有效”和“模板在已有修复基础上是否继续增益”。暂不把位宽压缩同时加入首个实验，以便知道效果来自哪个改动。
