## 一页摘要

1. **今年的核心不是“让 AI 写代码”，而是让人、模型、工具链形成可验证的工程闭环。** 典型闭环是：读题/需求 → 生成 RTL/HLS → 编译、仿真、综合 → 读取报错、波形和报告 → 反馈迭代 → 输出可复现工程。
2. **过程证据非常重要。** 应保留提示词、模型回复、工具调用、失败样例、人工判断、方案取舍和修复轨迹。AI 生成得快不等于工程可靠，人必须能解释并验证结果。
3. **Skill 不是一次性项目脚本。** 好的 Skill 应抽象出可迁移的工程经验，包括适用范围、步骤、输入输出、失败条件、校验方式和复用证据。
4. **RTL/HLS 本地智能体赛道重视“相对增益”。** 大模型裸跑很强不一定占优；较小或专用模型配合优秀智能体，若能显著提高通过率、稳定性并降低墙钟时间，反而可能得分更高。
5. **自主选题赛道重创新价值，不鼓励无意义堆复杂度。** 可以从前沿论文或其他学科中抽取一个关键思想，把它缩小成手头板卡能验证的问题，再证明其泛化价值。
6. **具身智能赛道必须形成真实闭环。** AI PC 负责端侧感知、理解、决策和规划；FPGA/Zynq 必须承担实质性的实时处理、接口、同步、控制或安全功能，不能只点灯、连蓝牙或充当普通转接板。
7. **统一环境、可复现和客观测评是出题人的强烈偏好。** 漂亮报告不能替代可综合代码、实测数据、原始日志和可重建环境。
8. **学习层面不要让 AI bypass 大脑。** AI 可以快速补齐信息和具体实现，但时序/组合逻辑、接口协议、系统划分、失败诊断和高层判断仍要自己掌握。

## 赛道一：RTL/HLS 本地智能体设计

### 讲者真正想考什么

- [录音] 不是比较谁调用了一次最强模型，而是比较谁能让智能体稳定生成正确、可综合的代码，并用工具反馈自行纠错。
- [录音] 一个好的智能体不应无休止调用 EDA 工具或消耗大量 token；应减少无效迭代，尽快从错误走到正确结果。
- [录音] 公开 benchmark 用于开发，最终通过隐藏题集检验泛化；统一云环境部署后再投题，不能在评测过程中临时改方案。
- [PDF] RTL 使用 Verilog/SystemVerilog，HLS 使用 Vitis HLS C++；参考数据集为 VerilogEval v2 和 HLS-Eval。
- [PDF] 分级判定：RTL 为“可编译 → 仿真通过 → 可综合”；HLS 为“可解析 → 可编译 → 测试用例全部通过 → 可综合”。统一目标器件为 `xczu3eg-sbva484-1-e`，时钟约束 5 ns，同时报告 pass@1 与 pass@5。

### 环境与模型边界

- [PDF] 开发阶段不限平台；验证阶段提供 ROCm 环境。
- [PDF] 模型须在单张 32GB 显卡中完整容纳，不允许跨卡；不设参数量上限，以显存为约束。上下文长度自定，但必须在 `MODEL.md` 和报告中如实声明。
- [PDF] 允许微调或使用硬件专用开源模型，但微调权重、来源、版本和训练数据来源都须声明并开源。
- [录音] 开发时可以先用商业 API 做探索，但最终应考虑量化、上下文长度、缓存和本地推理后端，保证方案可在统一 AMD 单卡环境运行。
- [录音] 统一测评不应依赖临时联网搜索。需要用到的文档、知识和工具应提前放入可重建环境中。

### 评分权重（PDF）

| 评测项 | 权重 |
|---|---:|
| 题集加权通过率 | 30 |
| 相对同模型裸跑基线的提升 | 40 |
| 墙钟效率 | 10 |
| 智能体与技能包的工程质量 | 20 |

这里最值得注意的是 40 分的“增益”：`run.sh` 与 `run_baseline.sh` 必须使用同一推理服务和上下文配置；基线绕过智能体/技能包，单次生成、不重试、不调用工具。赛题要看的是智能体给同一个模型增加了多少能力。

### 推荐实施重点

1. 先固定裸模型基线，再开发智能体，持续记录每次改动对 pass@1、pass@5、可综合率和墙钟时间的影响。
2. 把错误分类：语法/编译、测试用例、时序/综合、接口与约束、工具调用失败；为每类错误建立最短修复路径。
3. 让智能体先分析再调用工具，设置停止条件和预算，避免“反复跑十几二十次才偶然成功”。
4. 对 prompt、检索材料、校验脚本和工具反馈分别做消融实验，证明增益来自哪里。
5. 优先追求稳定性：缩小 pass@1 与 pass@5 的差距，而不是只展示一次成功。

## 赛道二：具身智能

### 必须成立的系统链路

`传感/输入 → AI PC 本地感知与理解 → 任务决策/规划 → PC 与 FPGA/Zynq 通信 → 实时控制/执行 → 状态与异常反馈`

- [PDF] AI PC 必须作为上位机，运行端侧 AI 推理、任务决策、人机交互或系统调度。
- [PDF] FPGA/Zynq 必须承担高速传感接入、实时处理、I/O 扩展、运动控制、安全逻辑、低延迟桥接、图像预处理、多传感器同步或自定义 RTL/HLS/AXI/Overlay 等至少一种实质功能。
- [录音] PCIe、USB/Type-C 等都可作为通信手段；接口形式不是重点，重点是数据流、延迟、同步、可靠性和异常处理是否说清楚。
- [录音] 单独 AI Demo 或单独硬件控制 Demo 都不是完整作品；“FPGA 只点灯或连蓝牙”明确不够。

## PYNQ 与 Skill：讲座最反复强调的共通主题

### PYNQ 的作用

- PS 端用 Python/Jupyter 组织应用、数据处理和系统控制。
- PL 端用 RTL/HLS 实现并行、低延迟或确定性更强的硬件功能，并封装为 Overlay。
- 硬件 bitstream/Overlay 可保持稳定，上层软件可持续变化，从而降低 FPGA 使用门槛。

### 一个合格 Skill 至少应包含

1. **适用范围**：能解决哪一类问题，依赖哪些板卡、工具版本和前置条件。
2. **可参数化输入**：例如滤波器类型、抽头数、数据宽度、时钟、接口和资源预算，而不是写死一个项目。
3. **步骤与理由**：每一步做什么、为什么按这个顺序、从工具中读取什么证据。
4. **自动校验**：黄金参考、测试台、日志解析、资源/时序检查、板级自测。
5. **失效条件**：哪些输入或环境下会失败，如何定位和恢复。
6. **复用证据**：在干净环境、另一块设备、另一种参数或相邻场景中成功复用。
7. **人的贡献**：抽象边界、判断标准、失败经验和取舍，而不是让 AI 机械总结一次成功流程。

讲者在第二段录音中用数字滤波器举例：只能生成当前这个滤波器的 Skill 通用性很差；若同一 Skill 能支持 8/64 抽头、高通/低通等不同配置，才真正体现工程抽象能力。

## 问答中最重要的学习观

- AI 会显著缩短“查资料和写具体实现”的时间，但不会自动赋予对底层原理的掌控。
- 时序逻辑与组合逻辑、PCIe/接口协议、硬件资源、工具报告和失败机理仍需自己逐步学习。
- 人必须对 AI 结果做可靠性把关；否则系统越复杂，出错时越无法定位。
- 不要把理解与判断的主动权交给 AI。需要保留自己的问题定义、推理、实验和结论。
- AI 特别适合帮助初学者接上原本断裂的信息链，从论文或陌生领域快速获得起步知识；随后必须通过实验和复盘将知识内化。
- 每天哪怕只真正弄明白几个小点，也应记录下来。竞赛中的学习轨迹本身就是可展示的能力。

## 建议的参赛工作流

1. **选赛道并写一页约束表**：硬件、软件、模型、显存、工具版本、评分权重、最终证据。
2. **先做最小可复现基线**：从第一周就建立一键构建、一键测试和原始日志，不要最后补。
3. **建立指标账本**：每次实验记录版本、输入、环境、结果、耗时、资源和失败原因。
4. **把 AI 协作留痕**：保存关键 prompt、回复、采用/拒绝的建议、人工修改和工具反馈。
5. **先形成闭环，再扩功能**：RTL/HLS 先打通生成—验证；具身智能先打通感知—执行；自主选题先完成最小创新验证。
6. **持续做消融和对照**：裸模型 vs 智能体、软件 vs FPGA、优化前 vs 优化后、单次成功 vs 多次稳定。
7. **中期开始抽象 Skill**：从真实失败中提炼，不要到提交前让 AI 现编 README。
8. **用干净环境复现**：换机器、换参数或换队友执行；所有隐含步骤都应显式化。
9. **报告直接映射评分表**：每一分都对应代码、测试脚本、原始日志、表格和可重复步骤。
