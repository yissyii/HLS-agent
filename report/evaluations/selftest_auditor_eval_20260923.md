# 自建测试审核助手评测报告（2026-09-23）

## 结论

现有审核助手可以继续作为旁路检查工具，但目前不宜据此自动改测试台或候选代码。

在本次人工构造的三类数学任务中，规则选对时，36 个正确判据均获支持；110 个错误判据中，默认抽样检出 104 个、漏掉 6 个；穷举检出全部 110 个。另一方面，选错规则会导致方向相反的判断，两个格式异常输入会令审核函数抛出未捕获异常。

建议先修输入健壮性、明确抽样结果的证据强度、复核规则与题意的匹配，再做真正的新题闭卷评测，最后考虑自动决策闭环。不要先大规模扩规则或直接接入主流程。

## 1. 测了什么，以及没有测什么

- 对象：`agent/selftest/audit.py` 和当前三条规则，模块版本 0.2.0。它是确定性审核程序，不是另一位大模型。
- 规则：Gray 解码、固定位宽反转、置位计数。
- 位宽：1、2、4、8、12、16；单个无符号输入、无状态、完整输入域。
- 人工构造 153 个判据表达式：36 个正确表达式，110 个非等价错误表达式，7 个实际没有改变功能的“等价变异”。后者单列，不充当错误样本。
- 错误包含恒零、恒等、结果最低位翻转、屏蔽输出高位，以及仅在一个指定输入上出错。
- 另外测试 12 个规则语义错配场景和 12 个证据缺失／不适用／异常格式场景。
- 正式运行前冻结源码、样本、预算、随机种子；运行后源码哈希保持一致。没有边测边修被测模块。

本次是开发者构造的压力测试，不是第三方独立盲测。数学任务家族是已知的，样本及位宽是扩展的；部分正确表达式或错误变异在功能上相关，不能视为独立随机抽样。本报告的比例只描述本测试集，不代表真实比赛错误分布。

没有调用真实模型，也没有调用远程 Vitis：本轮测的是“审核程序能否识别给定判据中的错误”，不是模型生成测试台的成功率、RTL 仿真能力或官方正确率。所有测试包用显式响应构造；种子测试包只放一个输入，审核器再独立选择检查点。

## 2. 如何避免审核器给自己打分

使用单独编译的 C++ 程序为全部 153 个表达式穷举计算标签，不调用审核器的 `rules.py`：

- Gray：枚举二进制值，用 Gray 编码建立逆映射表。
- 位反转：用除以 2、取余及逐位累加实现。
- 置位计数：用 `count[x] = count[x / 2] + x % 2` 建表。

审核器内部对应实现分别为累计异或、字符串翻转、二进制字符串计数，两套实现结构不同。评测夹具自检 4/4 通过；全部 36 个正确表达式通过独立全域校验，单点变异均恰好改变一个输入。正式结果中 `fixture_error=0`，不存在未能构造的计分样本。

这降低了同实现自证的风险，但两套程序仍由同一开发方编写，不能替代队友独立审阅数学定义与代码。

| 指标 | 默认预算 4096 | 全域预算 65536 |
| --- | ---: | ---: |
| 正确判据获支持 | 36/36 | 36/36 |
| 正确判据被判冲突 | 0/36 | 0/36 |
| 错误判据被检出 | 104/110（94.55%） | 110/110 |

位宽不超过 12 时，4096 已覆盖完整输入域，两列复用同一次结果；不是重复实验。16 位用例分别实际运行默认抽样与全域检查。

### 单点错误是明显短板

16 位共有 65536 个可能输入。预先指定错误点为 3、181、48879（0xBEEF），三条规则共 9 个单点错误样本。

| 检查方式 | 检出 | 漏检 |
| --- | ---: | ---: |
| 4096 点，种子 20260923 | 3/9 | 6/9 |
| 4096 点，种子 7 | 0/9 | 9/9 |
| 4096 点，种子 101 | 0/9 | 9/9 |
| 穷举 65536 点 | 9/9 | 0/9 |

附加种子提前固定，只用于这 9 个大域单点样本；没有挑最好种子汇报，也没有把同一样本的多次执行当成新题。

具体反例：`gray_decode_w16_singleton_3` 在输入 3 时，正确答案为 2，判据返回 3。默认抽样返回 `supported`，穷举返回 `conflict` 并保存反例。

大白话：抽查没抽到那一个错误点，就可能说“目前没发现问题”。这不是全对证明。16 位默认主输入抽样比例为 6.25%；补充性质可能额外求值，但本次仍未消除漏检。

## 4. 规则选错时：不能自动判断谁错了

对三条规则的六种有序错配，分别提供“符合题意的判据”和“符合错误规则但不符合题意的判据”，共 12 个场景，均穷举 8 位输入域：

| 场景 | 实际结果 |
| --- | --- |
| 判据符合题意，但绑定了另一条规则 | 6/6 返回 `conflict` |
| 判据不符合题意，但恰好符合绑定的错误规则 | 6/6 返回 `supported` |

例如题目要求位反转，却指定置位计数规则：真正的位反转判据会被判冲突；错误地做置位计数的判据反而获支持。

这不是违反当前审核 API 的条件性约定：它检查的是相对于指定规则的一致性，原报告也明确标注 `binding_semantics=not_independently_verified`。但它确实是自动闭环前的关键风险。

引用原题文字只证明“这句话存在”，不证明“这句话支持这条规则”。即使输入域已经穷举，选错规则仍然会得到方向错误的结论。冲突不能直接解释为候选代码错或测试台错。

## 5. 不适用及异常输入

12 个场景中，10 个按预期返回 `inconclusive`：缺少绑定、未知规则、位宽不匹配、部分输入域、有符号输入、两个输入参数、其他测试包的证据、伪造引用、预算放不下锚点、17 位超出规则范围。

另外 2 个触发未捕获的 `AttributeError`：

- 规则绑定 JSON 为 `[]`：`'list' object has no attribute 'get'`。
- 规则绑定 JSON 为 `null`：`'NoneType' object has no attribute 'get'`。

位置：`agent/selftest/audit.py:46` 解析 JSON 后，第 47 行直接调用 `.get()`，未先确认顶层是对象；第 111 行异常处理不包含 `AttributeError`。评测驱动捕获并单独记录这两次崩溃，审核函数本身没有正常返回结果。

建议先做严格结构校验，明确返回“输入无效／无法判断”；不要只靠捕获所有异常掩盖程序错误。本轮只记录问题，未修改审核器。

环境：WSL `zcomp-amd-ubuntu`，g++ 11.4.0；评测源码和结果位于 Windows 挂载盘。正式评测总耗时约 315.75 秒，模型请求 0。

16 位计分样本共 26 个：

| 默认 4096 点 | 0.615 秒 | 0.363～0.711 秒 |

这些是本机观测值，包含读取及校验测试包、审核、报告落盘等开销；不是跨机器性能保证，运行中还并行执行了回归测试。每个 16 位判据只多花几秒即可全域检查，是值得优先验证的改进，但不能推广到数组、多参数或更大输入域。

现有回归：`tools.test_selftest`、`tools.test_selftest_v02`、`tools.test_selftest_study`、`tools.test_selftest_license` 共 49 项全部通过，耗时 20.870 秒；包含刻意失败场景，日志中的 `failed` 不等于单元测试失败。新增评测脚本自检另计 4 项，全部通过。

## 7. 下一步顺序与验收条件（尚未实施）

1. **先修健壮性。** 顶层及嵌套输入类型均做结构校验。`[]`、`null` 等应正常输出明确的无法判断原因，不能崩溃或获支持；增加异常输入回归。
2. **区分证据强度。** 展示层／后续消费方明确区分抽样支持、全域支持、规则语义未核验。不把 `supported` 翻译成“测试台可靠”或“官方正确”。对当前完整 1～16 位单输入任务，可评估默认全域审核或分层升级预算。
3. **把规则选择单独验。** 优先让队友审核这三条规则及题目绑定。无法确认匹配时不进入自动决策；选错规则的 12 个场景要成为闭环防护测试，而非强迫审核器把条件性比较结果改名就算解决。
4. **再做新题闭卷评测。** 冻结实现后，由另一位队员准备未见题目、参考判据、错误实现和不适用案例；运行真实模型生成，分别统计生成成功率、判据实际正确率、条件性审核误拒／漏判及无法判断比例。参考答案不能进入生成提示词。
5. **最后逐步闭环。** 起初只允许输出建议并请求复核；用独立结果验证改测试台或改候选代码是否真的提高功能正确率，防止把测试标准改松来获得通过。

尚未覆盖：真实新题分布、自动规则选择、人工锚点接口的系统性压力测试、32 位及更大域、数组／流／状态／reset、RTL 时序语义，以及自动修复的净收益。本次没有验证这些能力。
