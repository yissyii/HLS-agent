# Bench4HLS baseline vs agent 评测记录（2026-09-17 · extract_code 更新后 · 全量 170 题）

> 历史实验：本轮分数和配置保持原样；当前运行方式见 [项目状态](../design/instruction.md)。两轮使用重新生成的候选，未固定随机种子，跨轮差异不能全部归因于提取器改动；要做因果归因还需固定原始响应重放或重复对照。

## 摘要

在 Bench4HLS 数据集**全量 170 题**上，用**本地 vLLM 端点（127.0.0.1:8001）**重新对比「纯 baseline 一次生成」与「agent 独立生成 + 修复回路」两条入口。本轮与 9-17 沙箱版（`9-17-Bench4HLS-BLandAgent-ALL-SandBox.md`）记录的主要代码改动是：**harness 的代码块提取逻辑 `extract_code` 已被重写**（由「整个响应必须恰好是一个 cpp 代码块」的严格 `fullmatch` 匹配，改为「解析全部 Markdown 围栏、按 C/C++ 结构特征打分择优」的 ranked-fences 提取）。

本轮观察到以下变化：

- **baseline 端到端通过率 40.0% → 52.4%（+12.4pp，多通过 21 题）**；同时生成失败由 68 次降至 21 次，其中 `response_format_error` 52 → 9。由于重新采样，不能将新增通过逐题全部归因于提取器。
- **agent 几乎不变**：54.7% → 55.3%（+1 题），单轮相差 1 题，尚不足以判断提取改动对 Agent 的收益。
- **baseline vs agent 的差距从 +25 题（+14.7pp）骤缩到 +5 题（+2.9pp）**，与响应格式失败减少同时出现，支持进一步检验提取规则对比较结果的影响；尚不能据此分离提取、提示和采样因素。
- 出现了**新的反转**：kernel 大类上 baseline 反超 agent（10/20 vs 8/20），此前为 4 vs 7。

本轮仍保持零网络失败、零 csim 启动异常（与 9-17 沙箱版一致）。

> 本文基于本轮沙箱完整重跑的实际结果（`output/local_eval/20260917T123237360039Z-f045ed00/`），未复用任何历史候选或日志。两条入口仍独立采样（temperature=0.7、未指定 seed），因此逐题差异同时混合了提示词差异与采样波动；agent 侧的变化（如 compile 152→148）也需要重复实验才能判断来源。

## 初始生成与修复收益拆分

两条入口独立生成，不是同一候选的修复前后对比（baseline 传题目原文，agent 经 `agent/context/builder.py` 加 HLS 约束后重新生成，未复用 baseline 候选）。

| 阶段 | 沙箱版 | 本轮 |
|---|---:|---:|
| baseline 独立生成后 overall 通过 | 68 | **89** |
| agent 首轮（candidates[0]）overall 通过 | 82 | **89** |
| agent 最终 overall 通过 | 93 | **94** |
| agent 从自身失败首稿中挽回 | 11 | **5** |

- **修复挽回的 5 题**：Prob023、048、057、100、126。
- 本轮 agent 首轮通过 89 题，全部最终仍通过（未发现已通过候选被修坏）。
- agent 首轮通过 82 → 89（+7）：一部分来自格式提取改善（即使 agent 提示词要求「仅返回源码」，仍有个别响应被新提取逻辑更准确地解出），一部分是采样波动。
- 修复挽回 11 → 5（−6）：首轮失败数下降（88 → 81）之外，挽回率也从 12.5% 降到 6.2%，修复回路的净收益进一步缩小。挽回题集与上一轮几乎完全不重叠（仅 Prob057 重复），说明修复收益高度依赖采样。

## 问题分析（排除网络问题与 csim 启动异常）

本轮仍为**零网络失败、零 csim 启动异常**。问题集中在代码提取、编译与功能三类。

### 1. extract_code 更新基本消除了 baseline 的格式失败（核心差异来源）

baseline 的生成失败从 **68 次（40%）降到 21 次（12.4%）**：

| 生成失败类别 | 沙箱版 | 本轮 | 变化 |
|---|---:|---:|---|
| `response_format_error` | 52 | 9 | −43 |
| `generation_incomplete` | 16 | 12 | −4 |

- **`response_format_error` 52 → 9**：旧的 `extract_code` 用 `fullmatch` 要求「整个响应恰好一个 cpp 代码块」，模型一旦输出 Markdown 围栏 + 说明文字、或多段代码块即被拒绝。新的 ranked-fences 提取会解析所有围栏并按结构特征择优，因此绝大多数「带解释或多代码块」的响应现在都能正确抽出源码。
- 剩余的 9 题 `response_format_error`（Prob003、025、050、071、081、116、137、155、158）属于**没有任何可识别的 C/C++ 代码块**（或围栏语言标签非 C/C++、未闭合且无结构信号）的响应，提取器仍会按设计拒绝。
- **`generation_incomplete` 16 → 12**：这是 `max_tokens=4096` 截断（`finish_reason != stop`），与提取无关；数量小幅波动属采样。剩余 12 题集中在 sequential/combinational 的长实现。

**结论**：baseline 的 21 次生成失败中，9 次仍是「无可用代码」的格式问题，12 次是 token 截断。而上一轮被格式问题挡下的约 47 题里，本轮 **21 题端到端通过、9 题转入编译失败、19 题转入功能失败**——即格式修复把「生成失败」转成了「真实的编译/功能失败」，这才是这些题目的真实难度所在。

### 2. 编译错误

| 入口 | 编译错误数 | 变化 |
|---|---:|---|
| baseline | 24 | 15 → 24（+9） |
| agent | 21 | 14 → 21（+7） |

- baseline 编译错误题目：Prob004、006、017、021、036、041、042、057、059、065、072、078、085、086、097、101、108、110、136、138、143、150、163、169。
- agent 编译错误题目：Prob025、050、065、071、078、079、081、088、089、109、110、111、112、120、122、130、142、150、153、157、163。

baseline 的编译错误从 15 增到 24，是「进入验证的题目数增加（102 → 149）」的自然结果——之前这些题在生成阶段就被格式拦下，现在能进入编译并暴露真实的编译难点（类型转换歧义、不存在的成员调用等，与 9-17 观察一致）。agent 的编译错误 14 → 21 属采样波动（compile 通过 152 → 148）。

### 3. 功能错误（编译通过、csim 不匹配）

| 入口 | 功能错误数 | 变化 |
|---|---:|---:|
| baseline | 36 | 17 → 36（+19） |
| agent | 53 | 59 → 53（−6） |

- baseline 的功能错误从 17 增到 36，同样是「更多题目能进入验证」的结果：baseline 进入验证 149 题，其中 89 通过、24 编译失败、36 功能失败（149 = 89 + 24 + 36）。
- agent 的功能错误 59 → 53，仍集中在 sequential（33 题）与 kernel（8 题）：
  - kernel：8 题功能错误 + 3 编译错误 + 1 综合错误，仅 8 题通过 → kernel 仍是最难大类。
  - sequential：33 题功能错误，是功能错误主体（时序/状态机输出错拍、状态未持久化）。

`category_only` 反馈只告知「功能失败」、不给反例，模型难以定位时序/状态持久化问题，这一缺口本轮依旧。

### 4. 综合错误与超时

- baseline：综合错误 0 题，无超时记录。
- agent：综合错误 1 题（Prob154，kernel）、超时 1 题（Prob085，`tool_timeout`）；`generation_incomplete` 1 题（Prob139）。

综合错误极少，说明「csim 通过但综合失败」不是本轮主要瓶颈。agent 的超时与综合失败各 1 题，均为个别复杂 kernel 题。

## 关键结论

1. **提取更新后的本轮 baseline 通过数增加**：overall 68 → 89（+21，+12.4pp），生成失败 68 → 21，其中 `response_format_error` 52 → 9。因同时重新采样，仍需固定响应重放或重复实验量化提取器的独立贡献。
2. **本轮 Agent 通过数变化较小**（93 → 94）：其提示词要求「仅返回源码」，观察到的格式失败较少；单轮数据不足以断言提取改进无收益。
3. **本轮 baseline 与 Agent 的差距缩小**（+25 题 → +5 题，+14.7pp → +2.9pp）。格式提取是需要控制的比较条件；现有两轮结果不能单独确定编码能力、提示词或修复策略的贡献。
4. **修复回路的净收益被重新审视**：修复挽回 11 → 5，且「仅 baseline 通过」升至 17 题。在公平的格式口径下，agent 的剩余优势（+5 题）既包含提示词/约束差异，也包含采样波动，不能简单归因于「修复能力」。
5. **本轮 kernel 通过数量反转**（baseline 10 vs agent 8）。它是本轮观察；格式、截断、重新采样及类别反馈各自的影响需要独立对照，不能凭两轮计数作确定归因。
6. **基础设施依旧干净**：本地端点 + Linux Vitis 下零网络失败、零 csim 启动异常，5 道历史启动异常题中 4 道已通过、Prob152 现由 baseline 通过。
