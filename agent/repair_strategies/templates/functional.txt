Apply these steps to the implicated behavior. Select checks supported by the task and evidence; avoid changing unrelated code just to satisfy a checklist.

1. Establish the contract. Identify the failing output or operation and its required relationship to inputs. Determine whether one invocation evaluates combinational logic, advances state, or processes a transaction. Do not equate a test cycle with an RTL clock or function call unless the task establishes that mapping.

2. Inspect the released evidence. Distinguish value mismatches, assertions, explicit runtime exceptions/deadlocks, and generic failure/exit summaries. Start with the earliest relevant failure whose order is reported; it may not be the first failure of the run. Use supplied inputs, expected/actual values, indices, signals, and history. Missing or omitted fields are unknown. Trace concrete execution only when enough inputs and state are known; otherwise inspect source-level contract violations without inventing a trace.

3. Follow the relevant dependency path. Trace backward from the failing output through expressions, branches, indices, and state. Check widths, signedness, intermediate expression types, truncation, shifts, and bounds where implicated. Preserve specified wraparound, saturation, rounding, and comparison semantics; widening every value is not a general fix. For explicit runtime exceptions, inspect the operation and its reachable conditions instead of masking it with an arbitrary output. For explicit deadlock evidence, inspect blocking operations and producer/consumer ordering while preserving the protocol. A generic timeout or nonzero exit establishes neither cause.

4. Check state and timing only when required. Distinguish state before the invocation, required current outputs, and next state. For simultaneous updates, compute from the appropriate old values before committing next state; sequential C++ assignments may otherwise consume an already updated value. Follow specified reset polarity, reset/enable priority, hold behavior, and output observation point. Required state must persist across invocations; temporary calculations must not acquire unintended persistence. A cycle number alone does not prove a one-cycle offset. Add delays, reset logic, handshake changes, or persistent variables only when supported by the contract and source.

5. Make a coherent correction. Choose a cause supported by the task and available evidence, and update directly affected computations or transitions consistently. Use references to check applicable APIs or patterns, not to replace required behavior. Incomplete observations do not prevent fixing a clear source-level contract violation. If no change is supported, preserve the candidate rather than manufacture a different one.

6. Review the change. Recheck supplied relevant counterexamples that can be evaluated with available information, plus nearby specified boundaries or transitions affected by the edit, such as a touched reset/enable branch or signed boundary. These are reasoning checks, not executed tests; do not claim validation passed. Return only the complete replacement source as required.
