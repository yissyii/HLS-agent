Apply these steps to the concrete synthesis-stage failure, using the supplied tool configuration and diagnostics.

1. Identify the failing operation. Read the diagnostic code, message, location, and implicated call path. Separate front-end C++ errors, unsupported constructs, interface/storage restrictions, and scheduling or resource constraints. If the message reports syntax, types, declarations, or API misuse, correct that source-level cause first. A synthesis-stage label or a final synthesis-failed summary does not prove an unsupported hardware construct.

2. Establish the behavior that must survive restructuring. Preserve the top-level contract, valid input domain, arithmetic, state lifetime, stream ordering, and explicit performance requirements. Do not assume simulation passed unless its result was supplied. A synthesis repair must still preserve functional behavior even when no functional result is available.

3. Choose a supported equivalent only for the implicated construct. Check relevant calls, loop bounds, allocation, recursion, storage, types, and interface use against the supplied evidence and version-compatible references. Derive any fixed capacity, iteration limit, or work-stack size from the task's valid input domain; never truncate valid work to an arbitrary constant. Preserve reset and lifetime semantics when changing storage. Replacing a construct with an example is justified only when the example's preconditions and behavior match this task.

4. Handle scheduling and constraints precisely. For an explicit dependency or port conflict, inspect actual data dependencies, access patterns, and required ordering before changing storage or scheduling. Never declare a true dependency false. Do not blindly add unroll/partition/pipeline pragmas or change target device, clock, interfaces, or required performance to obtain a pass. A missed target or warning is a required repair only when the supplied acceptance criteria make it a failure. If meeting a requirement needs architectural changes, derive them from the constraints instead of silently relaxing the requirement.

5. Review the replacement. Check bounds, termination, interfaces, state, and ordering affected by the transformation, including valid boundary cases. Ensure the change addresses the concrete diagnostic without introducing unrelated optimization. If the evidence does not establish a supported transformation, avoid speculative rewrites. Return complete source without claiming synthesis, timing closure, or simulation success from reasoning alone.
