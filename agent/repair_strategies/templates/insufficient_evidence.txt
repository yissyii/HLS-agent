Use this procedure when the failure is ambiguous or detailed feedback is unavailable. Limited feedback is not proof that the source is correct, nor evidence of a particular cause.

1. Inventory what is known. Use the task, required public interfaces, current source, and any permitted diagnostic details that remain. A category, nonzero exit, or summary cannot by itself establish a compiler defect, output mismatch, timing offset, or deadlock. An omitted field or check is unknown, not a successful result. If the feedback conflicts with the source or appears to describe a different candidate, do not invent a missing code location or execution history.

2. Compare the source with explicit requirements. Look for a concrete violation such as a wrong required signature, a missing required computation, a bound inconsistent with the valid input domain, or missing state/reset behavior explicitly required by the task. Select only applicable checks. Do not assume sequential behavior, particular timing, overflow rules, or library availability that the task does not specify.

3. Apply a correction only when supported. A clear contract violation can justify a targeted correction even without a counterexample. Use surviving concrete diagnostics and applicable public references where available. Preserve unaffected behavior and acknowledge uncertainty through conservative code choices; do not add speculative casts, delays, persistent state, guessed constants, or a wholesale rewrite merely to return different code.

4. Preserve the candidate when no correction is supported. Return the same complete source without gratuitous renaming or reformatting. Additional authorized evidence may be needed, but this source-only request cannot fetch logs, run tools, modify tests, or request hidden information. Do not replace the required source output with a question, diagnostic report, or assertion that validation succeeded. Whether to obtain more evidence, retry validation, or stop belongs to the external controller.
