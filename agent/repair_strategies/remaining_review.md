# 三类策略审阅与验证 v0.1.2

这些合成案例用于人工审阅提示词，不进入知识库、不来自隐藏测试。预期行为是评测标准，不是模型已经做到的结果。

## 编译／链接

顺序：定位诊断与关联声明 → 区分问题来源 → 根据语义核对类型/API → 专门检查链接 → 一致修改并复核。

| 案例 | 期望引导 | 应避免 |
| --- | --- | --- |
| 缺少分号后出现多条名字/类型错误 | 检查上下文及级联关系，先处理能解释后续错误的根因 | 对每条后续消息独立改写算法 |
| HLS 头文件内报模板错误，调用点传参不匹配 | 看调用点、实例化信息与真实类型 | 修改工具头文件 |
| 重载歧义 | 明确目标运算语义和转换范围，再选合法表达式 | 为编译通过随意强转成 int |
| 未定义 helper，题目已定义 helper 行为且应由候选实现 | 核对声明/定义/签名，补齐正确实现 | 添加返回零的占位实现 |
| 公共依赖缺失导致符号无法解析 | 识别源码之外的依赖限制 | 猜构建路径、改外部接口、伪造库实现 |

验证重点：compile_error 应进入 compile；仅类别应进入兜底；非 repairable 不产生片段。外部依赖限制目前不会被本模块重新分类或自动重试，模板只是约束模型不要伪造代码修复。

## 综合

顺序：读具体失败 → 明确要保持的行为 → 找有依据的等价结构 → 区分调度约束与警告 → 检查改动。

| 案例 | 期望引导 | 应避免 |
| --- | --- | --- |
| synthesis 阶段出现 C++ 未声明标识符 | 先修源码前端问题 | 因类别是 synthesis 就添加 pragma |
| 不支持某种动态结构，题目给了最大合法规模 | 依据合法输入范围推导静态容量并保持语义 | 随意截断到固定常数 |
| 需要替换递归但没有可证明的最大深度 | 保留证据不充分的判断，找其他有依据的算法转换 | 随意设小栈导致合法输入失败 |
| 存在真实数据依赖造成调度限制 | 根据依赖、资源访问和验收约束调整结构 | 用 dependency false 掩盖真依赖 |
| 只有性能警告，没有相关失败验收条件 | 不把警告自动当作修复目标 | 修改器件/时钟或降低显式性能要求 |

验证重点：synthesis_error 保持 synthesis 路由；模板内部区分前端错误与硬件限制；不假设 csim 已通过。当前不新增细粒度综合根因分类器。

## 证据不足

顺序：清点已知与未知 → 对照明确题意 → 有依据才修改 → 没依据则原样返回，交由外部流程处理。

| 案例 | 期望引导 | 应避免 |
| --- | --- | --- |
| 只有类别，但顶层函数签名明显不符题目 | 修明确的接口违例 | 因缺反例而拒绝所有修复 |
| 只有类别，源码也看不出明确违例 | 保留完整源码 | 改变量名规避重复检测，随机加类型转换 |
| 结构化证据因预算被省略 | 将被省略值视为未知 | 把省略理解为没有错误 |
| 日志位置明显属于不同候选 | 不虚构位置/历史，依据现有源码与契约检查 | 强套旧位置修改无关代码 |
| 模糊 compile_or_csim_error 仍附有有用细节 | 利用剩余证据作保守判断 | 因兜底名称而忽略所有细节 |

验证重点：空反馈、类别字符串、验证器的详细信息未释放/结构化反馈省略格式均进入兜底；未知类别与基础设施错误不生成代码修复策略。

## 自动验证与效果验证的区别

`python -B -m unittest tools.test_repair_strategies -v` 验证各类路由、反馈边界、模板冻结及三个策略的 CLI 输出。模板字符串或路由测试无法证明模型遵循了指令，更不能证明修复率提升。

真实效果应分三组逐一对照：固定失败首稿、反馈、模型、工具、预算与 RAG 状态，对比原统一 repair.txt 与增加对应策略片段。先每个候选单次修复，按初始类别统计恢复率、独赢/独输、编译回退、原样返回及成本。证据不足组需同时区分“明确题意违例可修”和“无法支持修改”，不能只奖励生成了不同代码。

本轮不连接主流程，也不改变去重与停滞规则。没有真实模型/Vitis 的结果时，结论只能是模块验证通过、策略内容经过案例审阅。
